# Trace 归属、采集范围与存储优化方案

日期：2026-09-24。状态：核心代码和诊断日志优化已实施；Claude 与 Insurance 数据集 A 各 120 案最终验收通过，见 §13。

已完成优化前备份。本文保留原始设计依据；实际落地范围、验证与尚未完成项记录在 §13。

最新范围确认：Trace 只承诺采集经过本地模型中转的 LLM 流量。完全不经过该中转的业务请求，无法由 Trace 自动发现，也无法获取其输入输出。现有评测器保存的业务结果属于独立评测产物，可选用于页面展示，不作为 Trace 接入要求或本期必做能力。

新增存储优化要求：降低 DEBUG 日志和重复产物带来的磁盘占用，同时保持现有前端可查看的记录内容、交互、离线打开及导出能力。具体证据、顺序和不退化验收见 §12；实施结果见 §13。

## 1. 目标与范围

本期核心目标：

1. Insurance 模型请求没有 case 标记，本地网关记录依赖时间窗口归属，可能串 case。
2. 按受控实例通道登记和 execution_id 归属模型调用，区分未归属、采集异常与正常无模型记录。
3. 降低网关诊断日志和评测产物的重复存储，优化后前端记录展示效果不退化，不以丢失模型调用内容换取空间。

此前讨论的“零 LLM 调用也记录输入输出”已收窄：仅当现有评测器已经保存相关结果时，页面可选读取；不建设通用业务输入输出采集能力，不承诺任意被测系统都能提供这些数据。

用户确定的边界：

- 不修改 Insurance 被测系统代码，不要求其透传请求级 ID，不增加业务埋点。
- Trace 只承诺记录经过本地模型中转的 LLM 协议请求、响应和耗时，不扩展为业务内部全链路追踪；绕过中转的模型调用同样不在可观测范围。
- 现有 Insurance 评测器自己发起 `/v1/chat` 请求，因此能保存它持有的业务输入输出。这是评测器的已有能力，不是中转拦截能力，不推广为其他系统的强制要求。
- 不新增逐个业务接口适配、不代理业务 HTTP 流量、不要求外部系统上报整案输入输出，也不设计通用业务交互采集协议。
- 可选页面展示仅消费已有评测产物；没有这些产物时只展示实际采集到的 LLM 调用，不尝试补采业务数据。
- 优先落地单实例串行方案；多实例并发沿用相同机制，不在首期开发实例编排平台。
- 不依赖 Insurance 的 `tracing_enabled`、Agno tracing 或 Langfuse。

“不改被测系统代码”不代表现有共享流量天然可区分。当前已通过启动配置把评测专用 Insurance 实例、网关端口和 key 与普通开发/验证流量隔离，具体见 §13；没有修改被测系统业务代码或新增业务协议。

## 4. 归属方案的成立条件

一个通道对应一个评测专用的被测实例及其模型出口。必须同时满足：

1. 单通道同一时刻只执行一个 case。
2. 被测实例由本次评测独占，不混入人工请求、其他跑批或无法区分的后台任务。
3. 网关能通过固定的本地认证身份或独立入口识别通道。
4. 正常完整业务响应代表本轮模型工作已结束；如被测实例存在响应后继续调用模型的行为，则不能直接复用该实例连续登记不同 case。

这是一种在受控串行执行条件下建立归属的方案，不具备请求自身携带唯一 ID 时的无条件区分能力。一个共享实例同时处理多个无标记请求时，外部无法可靠判断调用属于哪个 case。

首期默认一条通道。需要 N 路并发时，使用 N 个隔离实例，分别配置业务端口、模型出口身份和必要的运行资源；每条通道内部仍串行。文件数量本身不会增加可支持的并发能力。

通道身份选择：

- 可使用网关认可的固定 key 映射到 lane_id，或者使用专用入口映射到 lane_id。
- key 只标识实例通道，不按 case 改写，不在 key 中编码 case，也不依赖被测系统热加载。
- 当前 LiteLLM 启动脚本默认使用 master-key 配置；实施前必须验证认证方式是否支持所选通道方案。不能假定换成任意 key 就会被接受，也不能为此直接关闭鉴权。
- 原始认证 key 不写入归属日志；登记配置使用通道标识及必要的安全映射。
- 若无法隔离共享的无标记流量，该通道不能启用“可靠归属”模式。

### 4.1 key、lane 与登记文件怎样关联

采用 key 映射时，中转依靠预先登记的固定映射识别 lane，不会从 key 内容自动推导实例或 case。需要成套配置的是：**Insurance 实例地址 + 该实例调用本地模型中转时使用的 key + lane_id**。

| 配置关系（示例） | 实例 A | 实例 B |
| --- | --- | --- |
| 评测器请求的业务地址 | `http://127.0.0.1:18062/v1/chat` | `http://127.0.0.1:18063/v1/chat` |
| 该实例模型客户端使用的固定本地 key | key A | key B |
| 中转配置的 key → lane 映射 | key A → insurance_1 | key B → insurance_2 |
| 按 lane 推导的登记文件 | `llm_gateway/run/attribution/insurance_1.json` | `llm_gateway/run/attribution/insurance_2.json` |

以上端口、key 和第二实例均为设计示例，不表示已配置或已启动。这里的 key 是 Insurance 访问本地模型中转的凭据，不是评测器访问 `/v1/chat` 的凭据，也不是中转访问真实模型厂商的上游 key。

建议由评测器与中转读取同一份静态绑定配置，避免各自维护不同的对应关系。示意结构如下，文件名和字段均为待实现设计：

```yaml
# 建议位置：llm_gateway/attribution_lanes.yaml
# 路径统一相对该配置文件解析，不依赖进程启动目录。
registry_dir: run/attribution
lanes:
  insurance_1:
    chat_url: http://127.0.0.1:18062/v1/chat
    gateway_key_env: INSURANCE_1_GATEWAY_KEY
  insurance_2:
    chat_url: http://127.0.0.1:18063/v1/chat
    gateway_key_env: INSURANCE_2_GATEWAY_KEY
```

`gateway_key_env` 是已有凭据的引用；中转加载配置时读取实际值，建立“请求凭据 → lane_id”的内存映射。日志不输出实际凭据。环境变量名本身不会出现在模型请求里，中转匹配的是模型客户端实际发送的 key。示意配置也不会自动修改 Insurance 的模型配置，接入时需核对二者一致。

两侧的具体使用流程：

1. 接入配置者登记实例地址、固定模型 key 与 lane 的绑定，核对该 key 已获网关认证支持；归属映射本身不授予访问权限。
2. 评测器启动时选择 `lane=insurance_1`，从同一配置取得业务地址与登记目录，锁定 `insurance_1.lock`。若另行传入 chat_url，必须与绑定一致，不能把实例 A 的请求登记到实例 B 的文件。
3. 每案执行前，评测器写入 `insurance_1.json` 的 case_id、execution_id 与状态；静态映射和固定 key 保持不变。
4. Insurance 发起模型请求时，使用它原先配置好的 key A，例如通过 `Authorization: Bearer <key A>` 发送给本地中转。
5. 中转从认证层或入口读取可稳定识别的凭据身份，查固定映射得到 `insurance_1`。
6. 中转按 `registry_dir / (lane_id + ".json")` 定位登记文件，读取当前执行信息并固定到本次模型调用。

```text
评测器选择 insurance_1
  → 请求配置中的实例 A
  → 更新 insurance_1.json

实例 A 发模型请求，携带 key A
  → 中转查静态映射：key A → insurance_1
  → 读取 insurance_1.json
  → 取得当前 case_id / execution_id
```

文件名直接由经过校验的 lane_id 推导，不另建一份容易不一致的“lane → 任意文件路径”映射。lane_id 限制为适合作为文件名的标识，禁止路径分隔符及路径穿越。

启动校验与边界：

- 同一个实际 key 不能同时映射到两个 lane；同一实例也不能通过不同别名重复登记为独立通道。
- 必需凭据引用缺失、绑定重复或路径无效时，拒绝启用相应评测通道，而不是任选一个默认文件。
- 已通过认证但没有 lane 映射的无标记请求，记录为未归属；认证未通过的请求按网关原认证策略处理。不能因为只有一个登记文件就自动把未知请求归进去。
- 缺失或损坏的登记文件不触发其他文件查找；执行中不改变该通道的静态绑定。
- 即使多开 Insurance 实例，若它们使用相同 key 和相同中转入口，网关仍无法区分。业务端口不会自动成为模型请求的一部分。
- 不同模型中转入口可以替代不同 key：入口在中转侧固定绑定 lane，后续查文件的规则相同。这是可选接入方式，不与 key 方案混为已实现功能。

因此，多实例负责提供独立执行通道；固定 key（或独立入口）负责识别通道；登记文件负责标明该通道当前执行的 case。三者各有职责，缺少通道身份时不能仅靠文件数量解决归属。

## 5. 最小登记结构与互斥

每个实例通道一份登记文件、一把独立且稳定的锁，例如：

```text
llm_gateway/run/attribution/
  insurance_1.lock
  insurance_1.json
```

文件归属按实例通道管理，不按 harness 名称或 run_dir 随意拆分。两个评测进程指向同一个被测实例时必须使用同一通道锁；注册阶段也要拒绝同一实例被重复声明为两个独立通道。

登记内容示例：

```json
{
  "schema_version": 1,
  "lane_id": "insurance_1",
  "run_id": "dual_datasetA_<stamp>/insurance",
  "case_id": "INS_A01",
  "execution_id": "<完整 UUID>",
  "state": "active",
  "owner_token": "<本次持锁运行的随机标识>",
  "updated_at": "<带时区时间>"
}
```

约定：

- `case_id` 表示案例；`execution_id` 表示这一次执行，跨批次、重跑、恢复重试均不复用。
- 一次完整执行内的模型重试、降级、续写使用同一个 execution_id，各模型调用仍有自己的 call_id。
- `run_id` 必须带批次上下文，不能仅使用多批次重复的字符串 `insurance`。
- 登记采用同目录临时文件加原子替换；锁独立于被替换的 JSON 文件。
- 评测器持锁覆盖通道使用期。PID、时间戳只用于诊断，不作为唯一所有权依据。
- owner_token 不一致的旧进程不能清理或覆盖新登记。
- 正常状态只有 idle、active、blocked。不增加自动过期后重新分配机制。
- 锁释放不等于被测实例已空闲。接管遗留 active 登记必须转入异常恢复，不能直接跑下一案。

## 6. 正常执行与模型归属

```text
持有通道锁，核对通道隔离与网关可采集
  → 生成 execution_id，保存归属与执行状态元数据
  → 原子写入 active 登记
  → 发送 Insurance 业务请求
  → 网关首次接收模型请求时按固定 key/入口映射确定 lane
  → 按 lane 定位登记文件，读取一次并固定归属
  → 记录模型成功/失败/流式结束，沿用首次归属
  → 评测器确认业务请求结束，按原有逻辑保存评测结果
  → 核对已接收模型调用的结束记录并生成本案切片
  → 登记转为 idle，允许下一案
```

网关给首次请求记录附加：lane_id、run_id、case_id、execution_id、attribution_source。后续模型记录通过 call_id 复用这一快照。

- 归属应尽可能在网关接收请求的边界固定，不能等上游返回后再读取当前登记。
- 实施时核对 LiteLLM 重试及流式回调的生命周期，避免重试分支重新读取下一案登记；必要时在同一网关入口层保存请求局部快照。
- 已固定的归属不受登记后续变化影响，迟到的结束回调仍属于原执行。
- 已判定未归属的请求同样固定该结果，不能在成功回调时因新登记出现而补绑。
- 未配置通道、idle、blocked、文件缺失/损坏、状态冲突，均记录为未归属，不用时间或正文相似度补猜。
- 已收到请求但没有结束事件时，保留不完整记录；有界等待结束回调，不把无限等待引入批跑。
- 尚未收齐结束事件或网关状态异常时，保留已采集的模型记录和已有评测产物，并报告采集不完整；通道暂不自动推进，交由恢复流程处理。

显式标记路径继续支持 Claude 等可控客户端。带合法显式标记的请求不被 Insurance 登记覆盖；来源冲突要明确报出。新可控跑批也应传递唯一执行关联信息或与之建立明确映射，不能只按重复的 A01 切片。

回调需要能证明整个采集区间运行正常，例如入口就绪检查及运行期日志写入失败的可观察状态。不能只根据“日志里没有行”宣布采集成功。具体利用现有回调还是增加极小的本地状态接口，在实现时确定，不扩大为业务追踪服务。

## 7. 超时、残留调用与恢复

客户端超时、断连、取消、评测进程崩溃，均不能证明服务端已经停止执行。

处理规则：

1. 将通道置为 blocked，保存异常原因和当前 execution_id，停止启动后续 case。
2. 已绑定的模型请求继续沿用原归属。
3. blocked 期间新出现且无法证明来源的请求记为未归属，不贴给下一 case。
4. 确认旧执行不可能再产生模型调用后，才允许重新变为 idle。首期可通过人工恢复或重建评测专用实例完成；本次方案不授权自动终止现有服务。
5. 恢复后重跑生成新的 execution_id，原失败执行保留，不覆盖其产物。

“等几秒没有流量”“当前模型在途数为零”“登记超过 TTL”都不能证明旧执行结束，因此不作为自动解除阻塞条件。

正常完整响应代表轮次结束这一条件，需要在接入验证中确认。如存在响应后后台模型任务，必须每案隔离实例生命周期或暂不支持该实例连续跑批，不能靠登记文件掩盖限制。

## 8. 零 LLM 请求的可见性与现有评测产物

### 8.1 本地中转不能采集没有经过它的请求

任意业务请求如果完全不经过模型中转，中转不知道该请求是否发生，无法获得其输入、输出、业务状态或总耗时。仅把系统的模型 base_url 指向中转，不能使业务接口也变得可见。

lane 登记最多让中转知道评测器声明的当前执行身份，不包含业务正文，也不能证明该执行确实走了直达路径。不应通过扩大登记文件字段来实现隐含的业务上报协议。

因此，“没有 LLM 记录”不等于“业务请求没执行”，也不等于“已确认零 LLM 调用”。可能是未调用模型、模型绕过中转或采集存在问题，必须按实际证据表达。

### 8.2 Insurance 评测器已经持有的数据

当前 `adapters/insurance.py` 是 `/v1/chat` 的调用方，自己知道发出的用户问题和收到的业务响应。它已保存：

| 已有产物 | 数据来源 |
| --- | --- |
| prompt.txt | 评测器发送的用户问题 |
| response.json | 评测器实际收到的业务响应或其现有错误记录 |
| meta.json、cases/<id>.json | 评测器记录的问题、答案、耗时、状态等 |

这些文件作为现有评测结果继续保留。它们不是中转捕获的数据，也不是任意 harness 都必须实现的 Trace 契约。其他系统没有这些文件时，不为其新增接口适配或要求上报。

撤回此前把新增 `request.json`、完整业务请求/响应统一格式、业务异常采集字段等列为本次必做项的安排。本期不建设这些能力；现有评测记录逻辑按原用途保留。

### 8.3 本期只补归属必需的执行元数据

评测器为受控登记保存 run_id、case_id、execution_id、lane_id 与执行/采集状态，并按 execution_id 保留模型切片。该元数据用于归属和恢复，不要求携带业务输入输出。

每次执行记录按 execution_id 保留，例如 `cases/<case_id>/attempts/<execution_id>/`；兼容目录如保留当前展示执行，应有明确的 selected_execution_id。重跑生成新 ID，不覆盖旧模型切片与归属记录。现有评测产物如与执行一同保存，应保持同次执行关联，不能混合旧响应与新模型调用。

## 9. HTML 与切片规则

核心页面按实际模型记录展示调用和归属。仅接入网关日志时，列表中只有可观测的模型调用，无法自动列出完全不经过中转的业务请求。

若当前评测器提供执行清单，可按该清单展示已知 case，即使没有关联模型记录；这只说明评测器知道该次执行，不代表中转发现了零 LLM 请求。不要求其他接入方额外提供业务数据或执行清单。

既有输入输出的页面整合是可选项，暂不作为本期核心交付或验收前提。如后续启用，规则如下：

- 只读取现有评测产物，不新增业务采集路径；标注“来源：评测器结果”。
- 有同次执行的业务结果时，可展示问题、最终输出、总耗时和状态；仅展示已有字段，缺失不补造。
- 无模型调用但有已有评测产物时，可以展示该产物；没有产物时，不承诺业务输入输出可见。
- wire-only 内容标为“模型请求/模型回复”，不能把最后一条模型回复冒充 Insurance 的业务最终输出；模型耗时之和也不能冒充业务总耗时。
- 不人为构造模型调用，不推断内部工具步骤、内部工具数或直达路由。

模型区域的状态区分：

| 情况 | 展示 |
| --- | --- |
| 已采集并完成的模型调用 | 展示请求、响应、耗时 |
| 评测器已知本案执行，但中转没有关联模型记录 | 未采集到 LLM 调用；不据此断言直达或业务输入输出已被采集 |
| 仅有网关日志，业务请求完全不经过中转 | 无法发现该业务请求，不自动生成零调用 case 或业务记录 |
| 已有模型请求，缺少结束记录 | 调用记录不完整 |
| 网关不可用、日志缺失/读取失败/损坏 | 采集异常，不显示为正常零调用 |
| 采集健康状态无法确认 | 采集状态未知；如启用可选评测结果展示，不影响读取已有产物 |
| 历史数据没有 execution_id | 标明旧版归属，保留原结果，不宣称已纠正 |

新执行按 execution_id 精确切片，时间只用于排序和性能分析。关闭新执行的时间窗口回退；未知身份进入未归属记录。历史模式需显式区分，不因兼容逻辑把旧调用混入新执行。

| 场景 | 预期 |
| --- | --- |
| 同通道相邻 A01、A02 | 各自 execution_id 的调用不交叉 |
| 相同 case 跨批次、重跑 | execution_id 不复用，历史产物不覆盖 |
| 同案模型重试、续写、备用模型 | 仍归同一次执行，调用自身可区分 |
| 两个隔离实例并发 | 固定通道映射正确，记录互不混合 |
| key A/key B 请求各自进入中转 | 分别映射到对应 lane，并读取对应登记文件 |
| 同 key 重复绑定、凭据引用缺失或 lane 路径无效 | 启动校验失败，不选择默认通道 |
| 评测器选择 lane A 却指定实例 B 地址 | 发送请求前拒绝配置冲突 |
| 已认证但未登记 lane 的无标记 key | 记录未归属，不查其他 lane 文件 |
| 两个评测进程抢同一实例 | 通道锁阻止第二个执行者 |
| 正常请求结束回调晚到 | 不重新读取下一 case 登记；仍归原调用 |
| A01 超时且后续有模型请求 | 通道阻塞，A02 不启动，未知新调用不误归 |
| owner 崩溃、遗留 active | 新进程不直接覆盖，先恢复通道 |
| 缺失/损坏登记或身份冲突 | 记录未归属/异常，不猜 case |
| 评测器已知 case，但没有关联模型记录 | 显示未采集到 LLM 调用，不推断直达或要求额外业务上报 |
| 仅接入模型中转，无业务产物或执行清单 | 模型采集正常工作；完全不经中转的请求不可见，不生成虚假业务记录 |
| 日志读取失败、写入异常或结束事件缺失 | 与正常零调用区分 |
| 仅有模型回复，没有业务最终响应 | 标明模型回复，不宣称是业务最终输出 |
| Claude 显式标记与 Insurance 登记共存 | 标记不互相覆盖，批次和执行身份可区分 |
| 历史文件缺少新字段 | 能打开并标明旧模式，不混入新执行 |

若另行实施可选评测结果展示，再验证：已有产物且零模型记录时能读取已有输入输出；缺少产物时不补采、不伪造；业务结果与模型回复分别标注来源，且属于同一次执行。这些不作为核心归属方案的验收门槛。

归属与恢复首先使用本地模拟请求验证，再在独占的评测实例上做小规模真实验证。无需为文档本身运行模型评测；本轮未执行上述实现验收。

### 12.2 必须保留的现有能力

用户要求：**优化不能影响现有前端记录和展示效果。** 这作为发布门槛，而不是仅检查页面能打开。

对同一批已捕获的数据，存储优化前后须保持：

- case 列表、调用数量、顺序、case/execution/call 标识和归属一致；不合并不同调用或不同执行。
- 完整 system、messages、工具定义/schema、工具参数与结果、模型回复，以及模型协议实际返回且当前已采集的 reasoning/thinking 字段保持可查看。
- Raw request/response 保持当前可见内容与结构；不能只保留摘要或工具名列表。
- 开始结束时间、耗时、usage/token/cache 信息、状态和错误保持语义一致；缺失值不能被改成零或伪造值。
- 整案总览、调用时间线、上下文统计与增长、工具展示、详情/Raw 切换、现有检索或筛选与复制能力保持可用，以实际现有 UI 功能为基线。
- 现有独立 HTML 的本地离线打开、分享能力不因优化新增本地服务、网络、CDN 或旁文件要求；已有 Excel 和分享包等导出保持可用。
- 旧格式读取与历史报告打开保持兼容。没有通过兼容性验收前，不删除旧字段或覆盖历史报告。

本要求保护当前系统已有信息，不承诺补出模型协议未返回或旧采集本来缺失的内容。归属修正有意改变错误 case 匹配时，需单独验证预期修正；存储等价性比较使用同一归属输入，不能把两类变更混在一起解释数据差异。

### 12.3 分阶段优化顺序

**第一阶段：诊断日志与保留策略。**

1. 核对并关闭常态 DEBUG 正文输出，常态保留运行状态、告警和错误摘要；调试时临时开启，限定持续时间和总量。
2. 对 `litellm.stdout.log` 设置大小/份数上限并轮转，轮转实现必须兼容正在写入的进程。不能把反复清空整个日志当作长期方案。
3. 不关闭用于 Trace 的结构化模型 callback，不截断其模型正文。诊断 stdout 降噪与结构化模型数据采集是两个独立开关。
4. 现有 HTML 主读取每案 JSONL/trace 及相关产物；调整 stdout 前仍需检查全部现有消费入口，确认没有功能依赖 DEBUG 正文。用相同模型响应样本验证降噪不影响结构化记录。
5. 列出旧 ZIP、过往发布物和带日志/虚拟环境的备份清单，作为后续归档候选；先核对引用及恢复价值，不在本轮自动删除。新代码备份继续排除日志、评测结果、依赖及运行状态。

**第二阶段：每案与网关数据的无损去重。**

1. 优先以每次执行的 `llm_calls.jsonl` 作为该执行完整模型记录的权威产物，让 trace.json 保存引用/索引而不是同样正文的另一份副本。先盘点 HTML、Excel、导出、重建与其他消费者，更新所有读取入口并支持旧的内嵌格式，再启用新写入格式；不能直接删掉 `trace.llm_calls`。
2. 对同一 call_id 的事件重复内容，可考虑输入只保存一次、结束事件仅存响应和结果元数据，通过 call_id 无损还原现有逻辑记录。必须覆盖只有结束事件、入口记录缺失、重试、失败与流式等情况；无法还原时保留必要原文并明确不完整状态。
3. 不以摘要替换模型上下文，不丢弃长工具结果，不减少采样，不把多轮中看似相同的请求当成同一调用。跨调用差量编码暂不作为首期实现，避免引入引用链损坏问题。
4. 网关全局 JSONL 的分段、压缩、归档需与解析器一起改造：按唯一 call_id/execution_id 跨段连接，不因轮转造成漏读、重读或错配。当前解析器只读单文件，不能先开启数据日志轮转再补读取支持。
5. 历史模型源记录只有在持久化的每案权威记录已完整校验、未归属和不完整调用已另行保留、重建/导出无需被移除段时，才能进入独立的保留策略。采集中的数据、恢复中的执行与仍被引用的数据不自动清理。

每次执行目录中完整模型记录可以与全局采集日志暂时重叠，以保证持久化和恢复；目标是有边界的保留，而不是为了“零重复”牺牲完整性。具体分段大小、压缩阈值和保留时长待实测配置，不在此虚构节省比例或自动删除期限。

**第三阶段：HTML 内部数据体积。**

- 优先评估把内嵌数据中的重复值无损去重，或使用可离线解码的内嵌压缩载荷；页面加载时恢复与现有 UI 相同的数据结构，不减少可查看字段。
- 若采用压缩，解码能力必须随 HTML 提供或已被目标浏览器可靠支持，不依赖网络下载；兼容性和首屏加载需实际验证。
- 展示字段可从权威 Raw 数据按原逻辑生成，避免把相同文本保存多份，但必须对生成结果逐字段比对，不能借机改变展示口径。
- 不默认改成 HTML 外链 JSON，不要求用户启动 HTTP 服务，不通过删 Raw、隐藏工具 schema、砍历史上下文或只显示最近调用缩小报告。
- 若当前独立 HTML 的完整展示要求使某部分副本仍然必要，接受这部分体积；日志降噪和内部产物去重已可独立推进。

### 12.4 验证与回退

先选择已有大报告及小型代表样本建立基线，覆盖 Claude、Insurance、长上下文、多工具、模型返回 thinking、失败/流式记录、历史旧格式，以及没有关联模型记录的已知执行。

| 验收项 | 通过标准 |
| --- | --- |
| 模型记录等价 | 相同归属输入的调用集合、顺序、原始请求响应及元数据逐项一致；引用/压缩后可无损还原 |
| 前端数据等价 | 优化前后的前端逻辑 payload 语义一致；中文、换行、转义及长文本不丢失 |
| 实际页面验证 | 打开代表报告，检查总览、调用详情、Raw、上下文/工具展示和现有交互；不能仅比较文件哈希或做加载冒烟 |
| 离线与导出 | 独立 HTML 断网后仍能打开，现有复制与导出可用，Excel/分享包和重建入口无回归 |

| 空间收益 | 使用同一批固定数据比较优化前后逻辑大小和实际磁盘占用，分别统计 stdout、模型原始记录、每案产物和 HTML；不拿不同批次直接比较 |
| 性能 | 在代表性大报告上比较首屏、切换调用及展开 Raw 的耗时和内存，不能以明显的前端卡顿换取空间 |
| 故障与回退 | 引用缺失、解码失败或格式不兼容明确报错，不静默显示空记录；保留旧产物，可回退旧格式读取和生成 |

首次生成新版报告写入独立目标进行比较，验收后才切换默认生成方式。只读核对、方案记录并不构成上述实现已通过验证；本次没有清理历史文件、改变日志级别、关闭采集或修改前端。
